# Architecture

Linked Hardcore: any number of Fabric servers behind a Velocity proxy. All
players share one linked life pool — there are no groups. When any player dies,
everyone is set to spectator and transferred through the proxy to whichever server
is currently `READY`; if none is ready yet, players wait (spectating) until one
becomes available. The server they left is wiped and regenerated by an external
agent, then becomes ready to receive the next transfer. Ping-pong forever.

```
                    +------------------+
  player  --------> |   Velocity proxy  |
                    |  linkedhardcore   |
                    |  (plugin)         |
                    +---------+--------+
                              |
              +---------------+----------------+
              |                                  |
    +---------v---------+            +-----------v---------+
    |  Server A         |            |  Server B           |
    |  Fabric mod       |            |  Fabric mod         |
    |  (same jar)       |            |  (same jar)         |
    +---------+---------+            +-----------+---------+
              |                                  |
        config/linkedhardcore/            config/linkedhardcore/
        status.json, reset.request.json   status.json, reset.request.json
              |                                  |
              +----------------+-----------------+
                               |
                    +----------v----------+
                    |  Sisyphus (external) |
                    |  watches files,      |
                    |  stops/restarts,     |
                    |  deletes worlds      |
                    +---------------------+
```

## Component responsibilities

### Velocity plugin (`velocity-plugin/`)

- **Tracks backend lifecycle.** One `ServerStatus` per backend, with an explicit
  state machine (below). `ServerLifecycleListener` marks a server `LIVE` when a
  player connects and back to `READY` when its last player leaves (a `RESETTING`
  server is never touched this way).
- **Holds the linked player pool.** All players share one life pool — there are
  no groups. The proxy transfers every connected player on a death.
- **Listens on the messaging channel.** `ProxyMessageListener` handles
  `PLAYER_DIED`, `TRANSFER_READY`, and `RESET_COMPLETE` (see `PROTOCOL.md`).
- **Routes transfers.** `TransferHandler`:
  1. ACKs the death.
  2. Picks the first `READY` backend (other than the source) as the destination.
     If one exists, sends `PREPARE_TRANSFER`; otherwise sends `WAIT_FOR_SERVER`
     and holds a pending transfer.
  3. On `TRANSFER_READY`, transfers every player on the proxy to the chosen
     destination via `createConnectionRequest(...).connect()`.
  4. Marks the vacated server `RESETTING`.
  5. Signals the external agent via `ResetSignaller`
     (file impl: `reset.request.json`; a webhook impl is a noted alternative).
- **Death counters.** The proxy persists the authoritative per-player totals in
  `death-counters.json`, broadcasts snapshots to backends, and the Fabric mod
  renders them in a sidebar. World resets do not erase the totals.
- **Current run timer.** The proxy measures shared play time with a monotonic
  clock, pauses when everyone is offline, and checkpoints `run-timer.json` every
  second during play. It freezes the timer on an accepted death and resets it
  after a successful transfer. Backends receive `RUN_TIMER` snapshots and render
  `HH:MM:SS` above the death totals in the same sidebar.
- **Polls readiness.** `StatusPoller` reads each backend's one-second
  `status.json` heartbeat. A backend is `UNAVAILABLE` until it reports a fresh
  unused `ready` + `playerCount 0` snapshot matching its durable world identity.
  Pending resets require the expected request ID and a new boot/world generation.
  Stale heartbeats make a backend unavailable without cancelling its reset.
  Used empty worlds remain `LIVE` for reconnects; they are not fresh destinations.
- **Durable handoff recovery.** The current-world checkpoint includes the pending
  transfer, source/destination generations, run ID, accepted death record, and
  source cleanup. Restart and all-player logout preserve the ended-run boundary;
  an offline handoff does not require a plugin-message carrier. Timer commit replay
  is idempotent for its run ID. See `LIFECYCLE_RECOVERY.md`.
- **Reconnect routing.** A persisted `current-world.json` directs reconnects to
  the current run after logout and proxy restarts. An ended run first completes
  its recovered handoff to the next world. Pending/resetting backends
  reject new connections. Logout never promotes a used world to `READY`.
- **Status command.** `/linkedhardcore status` (alias `/lh status`) shows
  per-server state and who's online.

### Fabric mod (`fabric-mod/`) — identical on both servers

- **Death hook.** `PlayerDeathListener` subscribes
  `ServerLivingEntityEvents.AFTER_DEATH` (post-death, cannot be cancelled) and
  sends `PLAYER_DIED` for the player entity that actually died.
- **Countdown + spectator.** `TransferCountdown` handles `PREPARE_TRANSFER`: every
  online player is set to spectator and sees an on-screen action-bar countdown,
  then the mod sends `TRANSFER_READY` so the proxy moves everyone. On the JOIN
  event, players arriving in spectator are respawned into survival.
- **Reliability.** `ProxyMessenger` tracks pending `PLAYER_DIED`s; un-acked
  entries trigger a warning after `ackTimeoutSeconds` (see `PROTOCOL.md`).
- **Status reporting.** `StatusFileWriter` atomically refreshes `status.json`
  every second and on lifecycle events. The mod never touches world/playerdata
  files.

### External reset watcher (Sisyphus) — outside this repo

Only the contract is defined here; see `docs/RESET_CONTRACT.md`.

## Server state machine

Explicit and validated — illegal transitions throw instead of silently corrupting
state. `UNAVAILABLE` and `TRANSFERRING` are proxy-only safety states; the other
states mirror `status.json`.

```
UNAVAILABLE --verified unused world---> READY
READY --player joins------------------> LIVE
LIVE  --transfer starts---------------> TRANSFERRING
TRANSFERRING --all moves succeed------> RESETTING
RESETTING --matching new generation---> READY
```

Transitions:

| From       | To          | Trigger |
|------------|-------------|---------|
| UNAVAILABLE | READY      | fresh empty unused world matches durable preparation |
| READY      | LIVE        | a player joins (group member arrives) |
| LIVE       | TRANSFERRING | linked transfer begins |
| TRANSFERRING | RESETTING | every requested connection succeeds and sources are empty |
| TRANSFERRING | LIVE | transfer failure; never reset automatically |
| RESETTING  | READY       | expected request acknowledged by fresh new boot/world |

## The seam: plugin messaging

The two modules are **deliberately decoupled**: zero compile-time dependency on
each other's APIs. They only communicate over `linkedhardcore:main` with a
byte-exact protocol. See `docs/PROTOCOL.md`.

- Mod → proxy: clientbound custom payloads (`PLAYER_DIED`, `RESET_COMPLETE`, `TRANSFER_READY`).
- Proxy → mod: serverbound custom payloads (`PREPARE_TRANSFER`, `WAIT_FOR_SERVER`,
  `ACK`, `DEATH_COUNTERS`, `RUN_TIMER`).

The proxy gatekeeps both directions: it registers the channel in its
`ChannelRegistrar` and sets `ForwardResult.handled()`, and it only accepts
messages from backend `ServerConnection`s — a client cannot impersonate the proxy
to a backend, and nothing leaks to the actual client.

## Configuration (known simplification)

The proxy and the mod each carry a small config file (`plugins/linkedhardcore/
config.json` and `config/linkedhardcore/config.json`). There are no group
definitions anywhere — all players form one linked pool, so the configs only hold
the server id and timing options. They are intentionally separate to keep the
modules decoupled.

## Deployment model

- **Distribution is one jar per server.** The Fabric jar bundles FabricProxy-Lite
  via Loom's Jar-in-Jar (`include(...)`), so the operator drops a single jar into
  each server's `mods/` folder. FabricProxy-Lite still runs as its own mod at
  runtime; its `config/FabricProxy-Lite.toml` generates on first launch and needs
  the Velocity forwarding secret (plus `online-mode=false` in `server.properties`).
- The Velocity plugin jar goes in `plugins/` with its `config.json`.

## Future enhancements (out of scope for the initial pass)

- UI/HUD elements for players (shared-life indicator, remaining lives).
- Webhook-based `ResetSignaller` for cross-host deployments.
- PING/PONG health-check between proxy and mods (the ACK mechanism already
  detects a dead channel on the exact event that matters).
