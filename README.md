# Linked Hardcore

Two or more Minecraft servers behind a Velocity proxy. All players share one
**linked life pool**: when any player dies, everyone on both servers is set to
spectator and transferred to whichever server is currently ready. If no other
server is ready yet, players wait (spectating, "Waiting for available server")
until one becomes available, then the countdown runs and they're moved (respawn
into play on arrival). The server they left is wiped and regenerated by an
external agent ("Sisyphus"), then becomes ready to receive the next transfer.
Ping-pong forever. Works with any number of players and any number of servers.

- **Velocity plugin** (`velocity-plugin/`): transfer routing, server lifecycle
  state machine, `/linkedhardcore status`.
- **Fabric mod** (`fabric-mod/`): death detection, spectator + on-screen transfer
  countdown, respawn-on-arrival, status file reporting. Installed identically on
  both servers.

The in-game death-counter sidebar also shows **Run: HH:MM:SS** for the shared
current run. It starts when the first player joins a configured backend, pauses
while everyone is offline, and resumes on reconnect. An accepted death freezes
the final time as **Run ended** throughout the wait and transfer countdown. The
timer resets only after the group successfully transfers into the next world;
a failed transfer leaves the final time frozen.

The proxy saves the timer in `plugins/linkedhardcore/run-timer.json`, outside the
resettable worlds. Ordinary server/proxy restarts preserve the elapsed time and
exclude downtime; active play is checkpointed every second. Pending death transfers
are checkpointed with their world identities and recover after a proxy restart.
When everyone disconnects, the proxy completes the handoff to a prepared new world
without requiring a player-carried countdown message. Install the updated
proxy plugin and Fabric mod on all backends to enable the display. When first
installed, timing begins at the first join; earlier play time cannot be recovered.

See `docs/LIFECYCLE_RECOVERY.md` for transfer recovery and container-state migration,
`docs/ARCHITECTURE.md` for the full picture, `docs/PROTOCOL.md` for the wire
protocol, and `docs/RESET_CONTRACT.md` for the reset-agent contract.

## Setup

### 1. Install the mod (server A AND server B)

For **each** backend server, in its own directory:

1. Set up a Fabric server for MC 26.2 (loader 0.19.3+), Java 25.
2. Drop **one jar** — `fabric-mod-0.1.0.jar` — into `mods/`. FabricProxy-Lite is
   bundled inside; no separate download/install step.
3. Set `online-mode=false` in `server.properties`.
4. Launch once. It will generate:
   - `config/FabricProxy-Lite.toml`
   - `config/linkedhardcore/config.json`
5. **Set the forwarding secret** (the only manual step, done twice — once per
   server): put the same value in `config/FabricProxy-Lite.toml`'s `secret` and in
   the proxy's `velocity.toml` (see below).
6. Edit `config/linkedhardcore/config.json`: set `serverId` (`"a"` on A, `"b"` on
   B) and `transferCountdownSeconds` (how long the on-screen countdown runs before
   everyone is moved). All players are linked into one life pool — no groups to list.
7. Restart the server. It writes `config/linkedhardcore/status.json`
   on boot: unused prepared worlds are `ready`; existing used worlds remain `live`,
   including while empty. Set `pause-when-empty-seconds=0` in `server.properties`.

### 2. Install the Velocity plugin (the proxy)

1. Run a Velocity 4.0.0 proxy (Java 25), and configure both backends in
   `velocity.toml`:
   ```toml
   [servers]
   a = "127.0.0.1:25566"
   b = "127.0.0.1:25567"

   [forced-hosts]

   [advanced]
   # required for FabricProxy-Lite modern forwarding
   player-info-forwarding-mode = "modern"
   ```
   and set the same `forwarding-secret` value as the two servers' FabricProxy-Lite
   configs.
2. Drop `velocity-plugin-0.1.0.jar` into `plugins/`.
3. Create `plugins/linkedhardcore/config.json`:
   ```json
   {
     "backendServers": {
       "a": { "serverId": "a", "statusFile": "<abs-path>/server-a/config/linkedhardcore/status.json" },
       "b": { "serverId": "b", "statusFile": "<abs-path>/server-b/config/linkedhardcore/status.json" }
     },
     "statusPollSeconds": 1,
     "statusStaleSeconds": 5
   }
   ```
   > Add one entry per backend under `backendServers` (any number of servers).
   > The `statusFile` path tells the plugin where each server's status file lives,
   > so it can poll for `ready` and write `reset.request.json` next to it. Adjust
   > for your directory layout. `statusPollSeconds` controls how often the proxy
   > checks server readiness (default 1). `statusStaleSeconds` is the maximum
   > permitted age of the mod's one-second status heartbeat before the backend is
   > treated as unavailable (default 5).
4. Restart the proxy.

### 3. Run Sisyphus (external reset agent)

This is a contract, not code in this repo. See `docs/RESET_CONTRACT.md`. In
summary: validate the reset request and the backend's fresh empty `resetting`
heartbeat, stop the JVM, wipe the world/player-data directories, write the
request's new unused world identity, consume the request, then restart. Retain
`reset.pending.json` until the proxy verifies the new boot and generation. See
`docs/RESET_CONTRACT.md` for the complete schema-2 sequence.

## Local development: two servers + proxy on one machine

Recommended ports (all on `127.0.0.1`):

| Process   | Port  |
|-----------|-------|
| Velocity  | 25565 |
| Server A  | 25566 |
| Server B  | 25567 |

1. Build (`./gradlew build`), then make three directories:
   `dev-proxy/`, `dev-a/`, `dev-b/`.
2. **Proxy:** download Velocity 4.0.0, put it in `dev-proxy/velocity.jar`, drop
   `velocity-plugin-0.1.0.jar` into `dev-proxy/plugins/`, and create
   `dev-proxy/plugins/linkedhardcore/config.json` with
   `statusFile` paths pointing at `dev-a/...` and `dev-b/...`. Run once to
   generate `velocity.toml`, then set ports 25566/25567, `modern` forwarding, and
   a secret.
3. **Servers:** install a Fabric server (MC 26.2) in `dev-a/` and another in
   `dev-b/`. Drop `fabric-mod-0.1.0.jar` into each `mods/`. Set
   `online-mode=false` and the server ports (25566/25567). Launch once, set the
   forwarding secret in each `config/FabricProxy-Lite.toml`, fill in
   `config/linkedhardcore/config.json` (`serverId` a/b + `transferCountdownSeconds`),
   restart.
4. Connect to `127.0.0.1:25565`. Use `/linkedhardcore status` (or `/lh status`)
   on the proxy console / in-game to see server states and who's online.
5. For iteration, follow the schema-2 executor sequence in
   `docs/RESET_CONTRACT.md`. Deleting a world and restarting without writing the
   matching generation identity is not sufficient to acknowledge a reset.

## Containers (Docker Compose)

The repo ships a `Dockerfile` and `docker-compose.yml` that run the whole stack —
one Velocity proxy plus two Fabric backends — with the reset loop handled by the
container orchestrator. A **single image** runs either role; `MODE=proxy|server`
decides at container start.

### Quickstart

```sh
# 1. Build the image (this runs ./gradlew build + Fabric/Velocity installs).
docker compose build

# 2. Set the shared forwarding secret (optional; a dev default is built in).
cp .env.example .env      # then edit FORWARDING_SECRET

# 3. Start the stack.
docker compose up -d

# 4. Connect to the proxy.
#    Minecraft server address: localhost:25577 (or ${VELOCITY_PORT})
```

The image build requires network access (gradle deps, Fabric installer + vanilla
server jar, fabric-api, and the Velocity jar are all downloaded at build time;
the runtime is then fully offline).

### Environment variables

| Variable | Default | Used by | Meaning |
|----------|---------|---------|---------|
| `MODE` | `server` | entrypoint | `proxy` runs Velocity, `server` runs a backend |
| `SERVER_ID` | `a` | server | Logical id written to the mod's `config.json` (`a`/`b`) |
| `FORWARDING_SECRET` | `linkedhardcore-dev-secret-change-me` | proxy + servers | Velocity modern-forwarding secret; injected into Velocity's secret file and FabricProxy-Lite (`FABRIC_PROXY_SECRET`) |
| `TRANSFER_COUNTDOWN_SECONDS` | `5` | server | On-screen countdown before the group is transferred (mod `config.json`) |
| `PROXY_DIR` | `/lh/proxy` | proxy | Runtime directory on the persistent volume; the image install remains separate |
| `MC_MEMORY` | proxy `512M`, servers `3G` | both | JVM `-Xmx` |
| `VELOCITY_PORT` | `25577` | proxy | Proxy bind port and host port mapping |

`FORWARDING_SECRET` is read from `.env` (gitignored; see `.env.example`). The
dev default works out of the box but is not secret.

### How the reset loop works in containers

The entrypoint performs world deletion after the JVM stops. The proxy writes a
unique reset request plus a durable expectation when a transferred source is
empty. The executor waits for the matching empty heartbeat, stops the JVM, wipes
its world/player-data directories, records the request's unused generation, and
exits. Docker restarts the container; the proxy accepts only the matching new
boot's fresh heartbeat. Used standby worlds are prepared when a death needs a
new run. Ordinary restarts and logout preserve the current world.

Reconnects use `plugins/linkedhardcore/current-world.json` to resume the current
run, including a pending handoff for an ended run. Proxy state now lives at
`/lh/proxy` inside the named volume; see `docs/LIFECYCLE_RECOVERY.md` before
recreating an older container whose state was stored under `/opt`.
All reset/preparation metadata lives outside resettable worlds. Schema-2
changes require updating the proxy, mods, and executor together; see
`docs/RESET_CONTRACT.md` for upgrade and validation instructions.

### Playing / operating

- **Status:** attach to the proxy console (`docker attach lh-proxy` or
  `docker compose logs -f proxy`) and run `/linkedhardcore status` (alias `/lh
  status`) to see each server's state and who's online.
- **Death:** when any player dies, everyone is spectated, counted down, and moved
  to the ready server. The vacated server resets itself automatically.
- **Full reset:** `docker compose down` removes the proxy; `down -v` also deletes
  `lh-data` (worlds + configs) for a truly clean slate.
- **Worlds:** the world dirs live in the volume; the mod/config are re-templated
  on every boot, so you only need to `docker compose restart` a server to re-apply
  changed environment variables.

### Notes & caveats

- Backends are only reachable on the internal compose network
  (`server-a:25565` / `server-b:25565`); only the proxy port is published.
- `depends_on: proxy` only orders the initial `docker compose up`; it does not
  gate the reset loop, which uses per-container restart policies.
- The runtime image uses a JDK (not a JRE) for maximum compatibility with the
  Fabric server; swap the base image to `eclipse-temurin:25-jre` if you want a
  smaller proxy-only image.
- Containers run as root for simplicity with the shared volume; hardening this
  to a non-root user is future work.

The built mod jar must contain FabricProxy-Lite nested:

```sh
unzip -l fabric-mod/build/libs/fabric-mod-0.1.0.jar | grep META-INF/jars

```

## Known limitations / future work

- UI/HUD for players (shared-life indicator, lives remaining) — not implemented.
- Sisyphus is a documented contract (`docs/RESET_CONTRACT.md`), not a shipped script.
- All players share one linked life pool; no per-player or per-pair life separation.
